# Этап 46 — Android Keystore и опциональная авторизация через HTTPS

**Статус: подготовлен как изолированный инкремент. Не включён в действующий Android-процесс и FastAPI.**

## Архитектура

- Серверный реестр Stage45 (`backend_security/device_registry.py`) хранит только хеши индивидуальных токенов `ar1_...` и поддерживает отзыв. Он **не развёрнут** на ПК владельца.
- Android `DeviceCredentialStore` сохраняет выданный устройству токен **только в зашифрованном виде**: AES-256-GCM, ключ генерируется в Android Keystore и остаётся неэкспортируемым. IV создаётся отдельно на каждое сохранение; ciphertext лежит в приватных `SharedPreferences`. При потере Keystore-ключа/порче ciphertext возвращается ошибка, токен не восстанавливается из воздуха.
- Действующие `backup_rules.xml` и `data_extraction_rules.xml` исключают SharedPreferences. Существующие пользовательские аудио/Room не трогаем.
- Новый `DeviceAccessTokenSource` — интерфейс получения токена из защищённого хранилища. `RemoteAiProcessor(String baseUrl, DeviceAccessTokenSource)` — **новый opt-in конструктор**; он отвергает HTTP и при отсутствующем/некорректном токене сообщает `AI_AUTH_REQUIRED` **до сетевого запроса**.
- В новом режиме `Authorization: Bearer ...` добавляется только к HTTPS `/v1/analyze`. Существующие защитные свойства OkHttp (отключённые redirect/proxy/повторы внутри одного запроса, ограничение M4A/JSON) сохранены.
- Действующий `AiProcessorFactory.create()` и `AiProcessingWorker` **не изменены**. Старый дебаг LAN HTTP остаётся рабочим, но **не становится безопасным** и не должен использовать Bearer. Активация нового конструктора произойдёт только после доступного проверенного HTTPS и безопасного спаривания телефона.

## Защита существующих данных

Для `DeviceCredentialStoreInstrumentedTest` используются *отдельные test-only* SharedPreferences и Android Keystore alias. Тест не меняет и не удаляет реальный токен владельца при запуске на устройстве.

## Тесты

- `RemoteAiProcessorTest` расширен: HTTP с источником учётных данных запрещён, нет токена/повреждён токен → `AI_AUTH_REQUIRED` до отправки M4A, правильный HTTPS заголовок при фиктивном транспорте, локальный отзыв действует при следующем запросе.
- `DeviceCredentialStoreInstrumentedTest`: отсутствующий токен, зашифрованное сохранение/повторное открытие, замена с новым IV, некорректный токен, изменение ciphertext, удаление Keystore-ключа, локальная очистка. Для реального запуска нужен Android эмулятор/телефон.
- Workflow `.github/workflows/ai-android-credentials.yml` запускает Android `testDebugUnitTest` и **компиляцию** instrumented tests на Ubuntu. `compileDebugAndroidTestJavaWithJavac` НЕ означает, что инструментальные тесты были исполнены.

## Что остаётся (следующие стадии)

1. HTTPS сервер с корректной цепочкой доверия и совпадением SAN/host; не выключать проверку сертификата; при собственном CA доверять ему только в debug конфигурации или надёжно установить CA.
2. Выдача реального индивидуального токена владельцем через доверенный канал (не через открытый LAN API и не в Git), спаривание и отзыв. Android UI/QR-приёмник пока не создавались.
3. Связать `AiProcessorFactory` с `DeviceCredentialStore` **только** после готового HTTPS, предусмотреть невредящий откат без потери Room и записей, проверить ошибки отсутствующего/отозванного токена на настоящем сервере.
4. Запустить instrumented tests на Android API 24+ и реальный HTTPS E2E на устройстве без реальных записей пользователя.
5. Раздельное согласие на облачную обработку: `AI_PROVIDER=gemini` не включается автоматически при спаривании. Рабочий провайдер остаётся Qwen3/LM Studio.

## Границы безопасности
- Android Keystore помогает защитить криптографические ключи, но сам по себе не создаёт end-to-end защищённого канала и не устраняет риски скомпрометированного телефона.
- Пока старый LAN FastAPI принимает HTTP без авторизации, защита из PR **не активирована**. Не открывать порт в Интернет; для выпуска реальных ключей необходима защищённая среда.
- Токен устройства не равен `GEMINI_API_KEY`. Gemini API-ключ остаётся только на сервере.
