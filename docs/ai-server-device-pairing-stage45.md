# Этап 45 — персональные токены Android-устройств (первый инкремент)

**Статус: код создан, но НЕ подключён к локальному FastAPI и НЕ активирован на телефоне.**

Зависимости: PR №5 (Android AI), PR №7 (HTTPS-only ASGI guard); этот PR сделан поверх ветки Stage 44. `master` и работающие процессы пользователя не изменены.

## Что реализовано

- `backend_security/device_registry.py`: `DeviceRegistry` с SQLite. Администратор вручную выдаёт каждому устройству уникальный токен `ar1_...` со случайными **256 битами**; в базе сохраняется только SHA-256 от токена с доменным разделителем. Реальный токен возвращается только вызывающему коду в момент выдачи. Секреты никуда не логируются, в GitHub и APK не помещаются.
- Хранятся случайный идентификатор устройства, не содержащая секрета подпись/метка, время выдачи и время отзыва. Реестр допускает до 32 активных устройств по умолчанию. Отзыв действует на новых запросах сразу, потому что проверка читает SQLite каждый раз.
- Реестр требует явной инициализации `initialize=True` с **абсолютным путём**, который существует вне Git-репозитория. Отсутствующая или повреждённая база должна блокировать авторизацию (fail closed). Символическая ссылка вместо DB отклоняется.
- `backend_security/lan_auth.py`: опциональный `token_verifier=registry.verify` с отказом при HTTP, неверном токене, дублированных заголовках и проблемах хранилища; если хранилище недоступно — `503 AI_AUTH_UNAVAILABLE`, а не пропуск запроса. Прежний single-token режим оставлен только для обратной совместимости с тестами Stage 44. `enabled=False` по-прежнему ничего не защищает.
- `tests/test_device_registry.py`: тесты генерации и отзыва токенов, отсутствия plaintext в DB, восстановления состояния после открытия файла, защиты от повторного предъявления отозванного токена, лимитов, неправильных входных данных и TLS-only.
- GitHub Actions автоматически проверяет и Stage 44, и Stage 45 тесты.

## Чего ещё НЕ реализовано

1. Сертификат TLS/HTTPS, доверенный установленному Android APK, и безопасный HTTPS endpoint. Нельзя включать режим токенов на нынешнем HTTP-сервере.
2. Безопасное спаривание: локальный административный процесс должен **вне сети и API** выпускать токен и показать QR-код/передать его по доверенному каналу. Нельзя размещать административную выдачу в открытом LAN endpoint.
3. Сохранение полученного токена в Android Keystore и HTTPS-заголовок `Authorization: Bearer` в запросе M4A; ни один токен нельзя помещать в `BuildConfig`, исходники, GitHub, логи или неподписанный QR на публичной странице.
4. Отдельный маршрут или локальная административная функция отзыва, только для владельца и без доступа клиентам. Токены нельзя автоматически экспортировать в логи.
5. Статическая токен-авторизация не определяет модель. **Gemini остаётся opt-in**: отдельное согласие перед отправкой текста расшифровки Google; Qwen3 — прежний рабочий режим.
6. Backend `AIRecorderServer/main.py` и `gemini_adapter.py` существуют локально на ПК владельца; не включены в Android GitHub-репозиторий. Никакая интеграция этого прототипа в уже работающий процесс не произведена.

## Требования к безопасному развёртыванию

- Для Windows файл SQLite должен размещаться **вне директории проекта** в закрытой папке владельца с ограничивающим NTFS ACL. Режим файла `0600`, передаваемый через Python, сам по себе НЕ обеспечивает нужную ACL-защиту Windows.
- Для тестовой HTTPS-конфигурации Android использовать стандартную проверку сертификата. При собственном CA использовать `debug-overrides` / доверие только debug-сборки; не устанавливать TrustManager «accept all» и не отключать проверку hostname.
- Если появится reverse proxy, FastAPI должен быть изолирован на loopback; только доверенное взаимодействие с proxy может сообщать фактическую схему соединения. Не доверять `X-Forwarded-Proto` от произвольного клиента.
- Секреты и ключ Gemini не хранить в Android; Bearer токен каждого устройства должен быть отзываемым.
- Прежде чем включать защиту, построить и проверить полный маршрут **телефон (HTTPS) → токен в Keystore → авторизованный FastAPI → Qwen3**, затем проверить отсутствие соединения с неверным/отозванным токеном и корректный rollback.
- Нынешний LAN HTTP доступ уже работал на реальном телефоне; он **не становится защищённым** только из-за появления этого PR. В Интернет его не открывать.

## Проверка

Команда для Python тестов на ветке:
```bash
python -m pytest -q tests/test_lan_auth.py tests/test_device_registry.py
```

На CI используется отдельный workflow `AI Recorder LAN authentication tests`.
Тесты не требуют Gemini ключей, локального аудио или обращения к Google. Выполнение GitHub Actions отдельно подтверждается по результатам конкретного run (не подменять предположением).

## Принятые технические решения

- Хранить только хеши высокоэнтропийных токенов, а не PIN/пароль. Токены формируются через `secrets.token_urlsafe(32)`, их нельзя угадывать перебором.
- Проверять реестр непосредственно на каждый запрос, чтобы отзыв сразу действовал у всех работников Uvicorn.
- Устройства не могут сами создавать аккаунты через открытый LAN API.
- При ошибках базы не делать «аварийный обход» авторизации.
- Сохранять `/v1/analyze` multipart `record_id/file` и исходный JSON без изменений.
